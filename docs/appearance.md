# Desktop appearances

## Local storage and migration

Desktop themes belong to the local app installation, independently of accounts and servers. The default directory is Electron userData/themes. Settings show the actual path and can copy the complete workspace to a different empty directory, or reopen an existing local workspace. The original directory is retained. The selected location is stored in theme-location.json as a single directory; .workspace.json identifies the local image origin, without user or server IDs. Older .scope.json markers remain readable for compatibility, without ownership checks.

On upgrade, old account/server directories (including custom locations in theme-locations.json) are copied into the common workspace. Imported IDs receive a deterministic suffix to preserve themes with identical IDs. Draft source files, assets and preceding saved versions are retained; invalid drafts remain available for repair. The most recently modified old selection is used when the common workspace is empty. Old directories are retained as backups. Reopening the common workspace does not repeat the import or reset local changes.

- .drafts/<id>/theme.json and source files are the editable workspace.
- .saved/<id>/<snapshot>/ contains immutable published versions. A completed snapshot is written and read back before .state.json is atomically replaced.
- .state.json stores selection, saved snapshot pointers, collection revisions and the migration marker. Only the app edits it.
- Current and preceding published versions are retained. Rollback publishes a new monotonic revision. If a current snapshot is damaged, the preceding valid snapshot is recovered; unreadable records and original files are preserved for inspection.
- .trash retains replaced/deleted draft directories. Canceling a preview retains its draft.
- THEMES.md is a short on-demand index. docs/ contains focused runtime/messages/media/confirmations guides and appearance.json for ordinary settings; chatter.d.ts/chatter-ui.d.ts supply signatures. templates/component/ and templates/html/ hold complete file examples; template.json holds ordinary styling. No source templates or full capabilities dump are embedded in the index.

On first load, the desktop reads /api/v1/user/appearance/legacy, which preserves raw appearance entries instead of filtering unknown older fields. Older servers fall back to /api/v1/user/appearance; a fresh login snapshot can seed migration if the server is unavailable. All valid profiles are materialized into local manifests/source files; active selection is preserved only for a previously empty workspace. Existing local profiles, selection and draft files are never overwritten by migration. .migration-backup.json retains the original collection, including any invalid entries, and migration errors are shown in settings. The database collection is not deleted. After successful migration, the desktop no longer reads or writes it for normal appearance operations. A pending migration can be retried in settings.

Ordinary appearances remain ordinary configuration. They need only theme.json with palettes, typography, geometry, materials, background and motion. No HTML is required. The existing CSS tokens, contrast correction, fonts, density, material and animation runtime apply these values as before. A null activeId selects the built-in appearance. Existing system/light/dark/scheduled palette selection is unchanged.

## Components and source files

Canonical contracts are shared/appearance.ts and shared/appearance-project.ts; run node scripts/sync-appearance.mjs and validate with --check. They are mirrored into the main process, renderer and legacy backend parser.

A component project's on-disk shell manifest is:

```json
{"version":1,"language":"tsx","scope":"workspace","entry":"App.tsx"}
```

The app discovers TSX, TS, JSX, JS, CSS, JSON and HTML files recursively, with up to 256 runtime files and 500,000 source characters across the complete project. theme.json, tsconfig.json, declaration files, node_modules and hidden directories are excluded. Components support named/default exports, relative imports, extensionless and index imports, @/ aliases rooted at the project, JS-to-TS import resolution, shared CSS side-effect imports and JSON data. The entry default-exports a React component. Bundled external modules are react, react-markdown, remark-gfm and @chatter/ui. Package installation and direct OS access are not exposed inside the running shell.

chatter.d.ts gives editor types for window.chatter. The generated tsconfig.json includes the @/ alias. Create component project in settings writes a working App.tsx, separate chat list, conversation and composer components, a stylesheet and editor support files. The native editor can still edit individual files, while Open files goes straight to the draft directory in the file manager.

HTML and React shells use one file-project format: entry in the on-disk manifest, with code in adjacent files. HTML entries end in .html and may reference their own JS/CSS; React entries default-export a component. source/sourceFile themes are no longer accepted. No compatibility conversion is performed. The internal profile adds the discovered files map; it is not written into theme.json.

navigator scope opens selected chats in the native conversation. workspace scope keeps its own message renderer and composer. The live bridge supports chat/folder summaries, pagination, search, active messages, generation state and user-triggered actions. Read generated THEMES.md/chatter.d.ts for the complete API. Route-aware shells subscribe with {navigation:true}; older shells still reload their initial overview on return home.

## Editing, preview and application

useChatterState({navigation:true, confirmations:true}) from @chatter/ui reads ThemeState (initially undefined) and opts the shell into custom routing/confirmation handling. Both options default to false; child components may call useChatterState() without disabling the root. Hook consumers share one state subscription whose options are combined across mounted consumers. Boolean option changes and unmounts release that consumer's claim; the isolated bridge also counts direct subscribe consumers and only disables a capability after its last owner leaves. Keep the navigation owner mounted across routes, and confirmations ownership mounted while rendering every pending card.

Workspace message media are exposed as images[{url,type}] and attachments[{url,name,filename,mimeType,sizeBytes}], including media-only messages. These are source references without injected authentication tokens. Data and functions are the primary API: authors create their own markup, layout, styles and animations, without mandatory cards, galleries or other predefined UI. @chatter/ui provides optional Markdown (messageId/content), Image (messageId/url/alt), MessageImages (message) and Attachments (message), plus useChatterState. The Markdown formatting engine and styles are shared with the native renderer: GFM, syntax highlighting, accents, layouts, image galleries and file/chat links. Native executable previews, diagrams, charts and questionnaires remain code in the isolated shell. Authors retain control through public chatter-* classes, className/style and Markdown component overrides; replacing a component also replaces its behavior.

imageSource(messageId,url,width?) returns a scoped image URL, not a remote authenticated URL. The isolated renderer can request only images belonging to the currently loaded message/variant. The trusted host parses actual Markdown references (including reference definitions, excluding code/raw HTML), resolves credentials privately, and the main process loads raster bytes with concurrency, MIME, size and timeout bounds. Tokens are never sent to the theme. Sources changing chat/variant are cancelled; removed shells release pending loads. General networking, arbitrary local files, active SVG/HTML and media execution remain unavailable. Failed images offer a retry. Custom markup can use openImage/downloadImage(id,url), openAttachment/downloadAttachment(id,index), openLink(id,url) and copyText(id,text); gesture and current-reference checks precede existing host viewer/download/link/clipboard callbacks. Viewers close back to the theme without switching the selected shell. Neither saved themes nor their source are rewritten automatically.

fullImageSource(messageId,url) returns an original-resolution scoped src without a thumbnail width. The theme can place it in any img/CSS background, including its own styled modal or panel. No native window or navigation is triggered. Optional Image, MessageImages and Markdown accept onImageClick(image): supplying it replaces their native-viewer fallback. image has chatId/messageId/variantIndex/url/source/alt, with source already pointing at the original. Image also accepts fullSize. The author owns selection state, placement, styling and dismissal; no viewer markup is prescribed. Close selections when their chat/message/variant is no longer current. A theme's keydown handler can consume Escape with preventDefault; only an unconsumed Escape navigates back. The independent recovery shortcut remains handled by the main process. The native fallback remains usable above the shell; host modal detection ignores hidden dialogs.

Documents can also be rendered entirely by the theme. readAttachment(messageId,index) returns kind/name/mimeType/sizeBytes/text, sanitized DOCX html and PDF pageCount. Text is the existing server extraction, which may be an excerpt; the original remains available for download. renderAttachmentPage(messageId,index,page,width?) returns PNG pixels for one PDF page as source/width/height/page/pageCount. Pages are one-based and requested on demand, with width 128-1600 (default 1000). The trusted host reuses native PDF/DOCX parsing and the same byte cache, scoped by source as well as filename. Read-only requests are limited to current attachment URLs/variants, bounded and cancelled on scope changes. Tokens and raw source bytes never reach the theme. Optional Attachments.onAttachmentClick passes a descriptor to the author's own viewer instead of opening native UI. Catch read/page errors and discard stale async results.

Outgoing attachments use chooseAttachments() (alias attachFiles()) from a user event. It opens only the system file chooser; it does not switch to native chat or upload anything. Exact selected files are held under owner-scoped, expiring opaque tickets, read sequentially, and prepared with the same format/size/compression logic as AttachModal. The theme receives state.composer.busy/error/items/limits, with stable item IDs, names, types and sizes. pendingAttachmentSource(id) supplies scoped pending-image previews; removePendingAttachment(id) and clearPendingAttachments() update the existing composer. sendMessage accepts empty text when attachments exist and sends through the normal chat handler. The theme owns the upload list/panel/modal; a file input or filesystem API is not exposed. Selection cancellation, unmounts and chat changes discard unfinished additions. Existing pending document behavior remains metadata-only before sending. Crop/import flows are unchanged.

Workspace messages expose content, streaming, reasoningContent, workLog and toolStatus. content remains the answer or the currently uncommitted streaming text for compatibility. When a preface is committed before a tool call, it moves into workLog; render both fields from the latest snapshot instead of caching text that disappears from content. Keep rows with work-log entries, reasoning or active streaming even when content is empty; avoid empty answer bubbles. streaming identifies the particular active message, whereas state.sending is conversation-wide.

workLog uses the native conversation's step selection and chronological entries: message/activity with text, or tool with call. Tool calls carry name, localized label (raw-name fallback), optional id, kind, target, status (running/error/returned/unknown), internal, confirmed, arguments, optional resultPreview and nested children. Labels, categories and error detection reuse the existing desktop implementation, without a backend catalog request. All entries are available for themes to design their own display, including internal calls; these data grant no tool execution capability. Results may be truncated, and unknown does not mean success. Render tool data safely as text/Markdown. For older records without interleaving metadata, available intermediate messages precede the legacy tool-call list. toolStatus is often already represented by a work-log activity/running call; avoid duplicates. The starter includes a separate WorkLog.tsx renderer. Current saved themes are not rewritten; their authors must adopt these additional fields.

Workspace themes receive per-message actions and variant state. copyMessage, downloadMessageDocx, sendMessageToTelegram, forkFromMessage, editMessage(id,text,expectedVariantIndex?), deleteMessage, regenerateMessage (optional hint), activateMessageVariant and speakMessage reuse the normal conversation handlers. Render operations listed in message.actions; state.labels supplies localized accessible labels. Use editableContent as the original editing source and capture its variantIndex when opening your own editor. Saving text and submitting a regeneration hint keep the custom shell visible. The bridge requires a user gesture and validates chat/message/current variant/available operation. openMessageEditor, requestRegenerationHint and reviewConfirmation are explicit native helpers, not the normal custom-form actions.

state.speech exposes idle/loading/playing/paused and the current message ID. pauseSpeech, resumeSpeech and stopSpeech use the shared TTS service. Pausing retains audio position and does not request generation again. Buffer decoding and cancelled generation results cannot restart stopped speech.

With subscribe(listener,{confirmations:true}), state.confirmations contains full cards: content nodes, fields, actions, ready/revision/busy/customizable and ID/title/summary. A shared projection reads the existing ConfirmationCard React props; it does not scrape the DOM or duplicate the endpoint logic. While opted in, all pending card controllers remain mounted, so fields and callbacks remain current. Supported content includes text, Markdown, code/JSON, email source, file diffs and grouped content. Inputs/selects and normal/review/persistent-permission/rejection actions reuse their actual callbacks. setConfirmationField updates the native state synchronously; runConfirmationAction(id,actionId,revision,comment?) executes the current enabled callback under the existing busy guard. Stale revisions, resolved requests, disabled actions and invalid values are rejected. The example waits for field acknowledgments before enabling actions.

Full custom confirmation rendering does not switch to native mode. Native controls remain the fallback when a theme does not opt in, a projected component is unsupported, or the shell fails. reviewConfirmation is an explicit escape to the native card. Separate starter components demonstrate message editing, hint forms, confirmation content, fields and actions without constraining the design. Read generated THEMES.md/chatter.d.ts for complete signatures; existing draft projects can copy the updated workspace declarations for editor completion.

Draft file changes are observed with filesystem events and debouncing, without polling. Before a preview or proposal, the desktop checks syntax and imports without executing model code. An already open draft preview refreshes when valid files change. Invalid edits keep the preceding preview visible, show file/line diagnostics, and disable application until repaired. After cancellation, filesystem edits cannot reopen the preview. Active appearance snapshots never follow draft changes automatically.

Only explicit user application saves/selects a new published snapshot. Native controls provide a Back to custom interface button in the native conversation and the chat library drawer. Settings opened from a shell return to that shell when closed. Escape and the independent recovery bar restore the saved appearance; Ctrl/Command + Alt + Backspace selects the built-in appearance locally. Changing accounts, servers or signing out retains the same local library and selection; local appearance loading and recovery are available without signing in.

## Images and portability

Uploaded raster backgrounds are stored locally, with an 8 MiB limit and PNG/JPEG/WebP/GIF signature validation. On disk, a theme refers to assets/<image>. In memory, the app uses a content-addressed chatter-theme URL; the protocol serves only validated image hashes in an initialized theme workspace. Paths, symlinks and arbitrary files are rejected. The isolated code surface does not receive a filesystem bridge.

Migration tries to copy owned /api/v1/images backgrounds to the PC. If a resource cannot be downloaded, the original server reference remains and settings report it. External HTTPS image links retain their original behavior. The database backup remains unchanged.

Export creates a ZIP containing theme.json, source and local assets. ZIP import creates a new inactive draft with a new ID. Old complete JSON exports still import. Archive paths and expanded size are bounded; traversal and symlinks are rejected. Copying a theme directory or importing its package preserves local raster resources across PCs/accounts.

## Bot integration

No theme instructions or state are injected into the system prompt, and theme metadata is not synchronized to the backend automatically. get_theme_docs() requests two blocks from the connected desktop: readme (the current THEMES.md guide for creating and editing themes) and state (directory/documentation paths, active theme ID, saved theme IDs/names and draft IDs). desktopVersion identifies the app supplying the guide. Source files are read on demand through the existing desktop file tools. The backend only forwards this request over appearance_workspace IPC; guide content can change with desktop releases without backend changes. The request has no file path argument, returns no theme source, and cannot propose or apply a theme.

The two exposed appearance tools are get_theme_docs() and suggest_appearance({id, checkOnly?}). The latter requires the draft folder ID, reads and validates that draft locally, then emits the existing confirmation card. checkOnly:true returns diagnostics without a proposal. Raw profiles and source maps are not tool arguments, and bot proposals do not save or apply files. Refresh documentation and state by calling get_theme_docs() again.

The old HTTP appearance endpoints remain for migration and older clients. The updated desktop does not use POST /api/v1/user/appearance or the server image-upload endpoint for its local themes. Chat layout remains a separate existing feature.

## Color regions

Each light/dark palette has background (application shell), text and accent. Optional surface controls the sidebar, header, composer, tools panel, title bar and settings window, with its own derived text and control colors. Optional chat sets the solid conversation color. The existing profile.background gradient/image is conversation-only and takes precedence over chat. Omitted surface/chat retain previous behavior exactly; Auto removes the corresponding override. The optional color fields require no additional migration or palette-preference change. The shared schema, capabilities and editor use the same names; legacy profiles still validate without adding fields.

## Surface materials

Optional profile.materials.panels and profile.materials.composer each contain opacity (0.55–1), blur (0–32px), shadow (none/soft/medium/strong), border (none/subtle/defined), and optional radius (0–24px, otherwise the global radius). Omission means exact legacy styling; Auto removes that region. These additive fields use the existing API, tools, saved variants and confirmation flow.

Only the background fill is translucent. Text/control colors are derived against worst-case black/white backdrops; fill opacity is applied exactly as requested. A low-contrast material produces an editor hint instead of a hidden opacity increase. Backdrop blur is static, bounded, and scoped to chrome/composer surfaces; it never filters the conversation or runs in scroll handlers. Panels above flat content may show no visible blur. Reduced transparency and browsers without backdrop-filter get opaque paint. Shadow and border use finite presets, not arbitrary CSS. Materials do not change measured row heights.
